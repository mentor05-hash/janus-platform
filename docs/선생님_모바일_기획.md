# 선생님 모바일 앱 기획서 (Teacher Mobile)

> 대상: 멘토링 플랫폼 선생님(멘토). 현재 선생님은 **웹(데스크톱)** 만 사용 가능하고
> 모바일 앱(학생·학부모 전용)에 로그인하면 "웹을 이용하세요" 안내만 뜬다.
> 이 문서는 **선생님용 모바일(태블릿 우선·폰 대응)** 을 신설하기 위한 기획이다.
> 작성 기준: 현재 백엔드(NestJS)·실시간(socket.io)·상담기록/알림/QnA 모듈은 이미 구현되어 있으며,
> 모바일은 **기존 API 재사용 + 모바일 UX 신설**이 원칙(재개발 아님, CLAUDE.md §10).

---

## ✅ 구현 현황 — 이 기획은 전량 구현·검증 완료

이 기획서의 로드맵은 **MVP 1단계 → 2단계 → v1.1 → v1.2 + 추가 확장**까지 모두 구현되어 데모에 반영됐다.
로그인 화면 「선생님」 원터치(`lt1`)로 진입해 확인할 수 있다.

| 영역 | 구현 내용 | 상태 |
|---|---|---|
| 진입 골격 | 역할 게이트 해제, 선생님 5탭(인박스·오늘·상담·기록·마이) | ✅ |
| ① 인박스 | `GET /me/inbox` 집계, 유형 필터, 상담신청 수락/거절, 질문 인라인 답변, 태블릿 2열 | ✅ |
| ② 상담 진행 | 채팅(읽음·입력중·미확인·무소음카메라·**파일 전달**) · 화이트보드(지우개·자동저장·**사진 위 필기**) · **WebRTC 음성통화**, 태블릿 2-pane | ✅ |
| ③ 상담기록 | 예약별/학생별 히스토리, draft→final 완료, 태블릿 2-pane | ✅ |
| 오늘 | 오늘 일정·이번 주 예정 + **근무 상태(근무중/휴게중/퇴근)** → 휴게·퇴근 시 신규 신청 게이팅 | ✅ |
| 마이 | 프로필·평점·응답률·프로필 완성도·예상급여 | ✅ |
| 전사 정책 | 역상담 오프라인 한정(본사)·크레딧 미소모(마스터) | ✅ |

> 상담 진행 도구(채팅·화이트보드·미디어·음성·파일)는 학생앱과 동일 소켓 스택을 재사용 — 신규 백엔드는
> 인박스 집계·근무 상태·역상담 정책 정도로 최소화됐다.

## 1. 배경 · 문제

- 선생님의 실제 근무는 **이동 중·상담 현장·태블릿 필기** 등 비데스크톱 상황이 많다.
- 그런데 지금은 상담 신청·질문 유입을 **웹에 접속해야만** 확인·응답할 수 있어 반응 지연이 크다.
- 학생 앱에는 이미 실시간 채팅·화이트보드가 있으나, 선생님은 웹에서만 참여 가능해 **모바일 상담 진행이 불가**.

## 2. 목표 (성공 지표)

| 목표 | 지표 |
|---|---|
| 유입 즉시 인지 | 상담신청·질문 알림 → 확인까지 중앙값 5분 이내 |
| 모바일 완결 | 상담 진행·질문 답변·기록 저장을 **폰/태블릿만으로** 완료 가능 |
| 기록 품질 | 완료 상담의 최종기록(final) 작성률 ↑ (현재 대시보드 '기록작성률' 지표와 연동) |
| 재사용 | 신규 백엔드 최소화 — 최우선 기능은 **기존 API 100% 재사용** |

## 3. 설계 원칙

1. **태블릿 우선(tablet-first), 폰 대응(phone-capable).** 기준 폭 3단계:
   - `≥1024`(태블릿 가로/데스크톱): 2-pane(좌: 목록/인박스, 우: 상세·상담 진행). 필기 화이트보드 풀사이즈.
   - `768–1023`(태블릿 세로): 1-pane + 슬라이드오버 상세.
   - `<768`(폰): 스택 내비게이션(전체화면 전환), 핵심 기능만 우선 노출.
2. **알림 → 액션 원클릭.** 알림 탭 시 곧바로 해당 상담/질문 처리 화면으로 딥링크.
3. **오프라인/약전파 내성.** 상담기록은 로컬 초안 자동저장 후 동기화(웹 기록은 이미 draft/final 구조).
4. **재사용 우선.** 화면은 신설하되 데이터·검증·권한은 서버 그대로(§10 이식 원칙).
5. **역할 게이팅.** 선생님(teacher) 역할만 접근. 관리자/HR는 계속 웹.

## 4. 정보구조(IA) · 화면

하단 탭(폰) / 좌측 레일(태블릿) — 5탭:

| 탭 | 화면 | 핵심 |
|---|---|---|
| 🔔 **인박스** | 알림·유입 통합 인박스 | 상담신청·질문·역상담·취소 등 유입을 한 곳에서 처리(최우선①) |
| 📅 **오늘/일정** | 오늘 상담·다가오는 예약 | 상담 진행 시작, 근무/휴게 상태 |
| 💬 **상담** | 진행 중/대기 상담 | 채팅·화이트보드로 상담 진행, 질문 답변(최우선②) |
| 📝 **기록** | 상담기록 목록·작성 | 기록 남기고 수정(최우선③), 학생별 히스토리 |
| 👤 **마이** | 프로필·급여·평가·설정 | 예상급여·받은평가·근무설정(차용 기능) |

> 폰에서는 인박스·상담·기록을 최우선 3탭으로, 오늘/마이는 축약. 태블릿에서는 좌측 레일 + 우측 상세.

## 5. 최우선 기능 (반드시 MVP)

### ① 유입 알림 인박스 — "들어온 것을 놓치지 않기"

**목적**: 상담신청·질문·역상담 제안·취소 등 **유입 이벤트를 즉시 파악**하고 바로 처리.

**구성**
- 상단: 미확인 배지(유형별 필터: 전체/상담신청/질문/취소/역상담).
- 리스트: 알림 카드(학생·유형·시각·요약) + **인라인 액션**(수락/거절/답변하기/열기).
- 실시간: 소켓 `notif:new` 수신 시 상단에 토스트 + 인박스 상단 삽입(이미 구현된 실시간 알림 계층 재사용).
- 푸시: 앱 미실행 시 OS 푸시(학생앱과 동일한 expo-notifications 토큰 등록 경로 재사용).

**재사용 API (이미 존재)**
- `GET /notifications` (목록) · `PATCH /notifications/:id/read` (읽음) · 소켓 `notif:new`
- 알림 유형 템플릿 이미 구비: `booking_requested`(상담신청)·`reverse_proposed`·`booking_cancelled`·`qna_assigned`·`qna_answered` 등(`notification-templates.ts`)
- 상담신청 수락/거절: `PATCH /bookings/:id/accept` · `/reject` · 역상담 `PATCH /bookings/:id/reverse-respond`
- 채팅 미확인: `GET /chat/unread` (이번에 신설)

**추가 필요(소)**: 인박스는 알림+미확인채팅+대기예약을 합친 뷰라, **집계 엔드포인트 1개**(`GET /me/inbox`)를 얇게 추가하면 왕복이 준다(선택). 없으면 프론트에서 3개 호출 합성으로도 가능.

### ② 상담 진행 · 질문 답변 — "모바일에서 끝내기"

**A. 상담 진행(예약 상담)**
- 오늘/상담 탭에서 상담 카드 → **상담 진행 화면**(태블릿=2-pane: 좌 학생요약/기록, 우 채팅·화이트보드).
- 도구: **실시간 채팅**(읽음·입력중 표시 신규) + **공유 화이트보드**(지우개·자동저장 신규). 둘 다 예약 room 기반, 이미 구현.
- 진행 종료 → 바로 ③ 상담기록 작성으로 유도, `PATCH /bookings/:id/complete`(완료는 기록 final 선행, §5-5).

**B. 질문 답변(QnA·건당)**
- 인박스/상담 탭의 "질문" → 질문 상세 → **담당(claim) → 답변 작성 → 제출**.
- 이미지/필기 첨부 가능(파일 업로드 재사용).

**재사용 API**
- 상담: 채팅/화이트보드 소켓(`chat:*`,`wb:*`), `PATCH /bookings/:id/confirm|complete`
- 질문: `GET /qna/posts` · `POST /qna/posts/:id/claim` · `POST /qna/posts/:id/answers` · `PATCH /qna/answers/:id/accept`
- 화상: 줌 입장 URL(`ZoomProvider`)은 상담 카드의 "입장" 버튼으로(모바일은 앱 스킴 연동)

### ③ 상담기록 작성 · 수정 — "남기고 고치기"

**목적**: 상담 후 핵심요약·숙제·향후방향·(내부)메모를 **모바일에서 작성/수정**, 완료 처리.

**구성**
- 상담 진행 종료 → 기록 시트(핵심요약·숙제·향후방향·메모·보호자공개 토글).
- **로컬 초안 자동저장**(draft) → "최종 저장"(final) 시 학생·보호자 공개. 완료(done)는 final 선행.
- 기록 탭: 내 상담기록 목록(학생별/최근순), 카드 탭 → 수정(같은 시트).
- 마스킹: 메모는 본인·관리자만, 학생/보호자는 final의 공개필드만(서버 규칙 그대로).

**재사용 API (이미 존재, CRUD 완비)**
- 작성/수정: `PUT /bookings/:id/note`(upsert, `saveState: draft|final`)
- 조회: `GET /bookings/:id/note` · 내 기록 `GET /me/notes` · 담당 학생 `GET /me/students` · 학생 개요 `GET /students/:id/record-overview`

> 세 기능 모두 **백엔드 신규 개발 없이** 모바일 화면만 신설하면 동작한다(인박스 집계 1개만 선택적 추가).

## 6. 상담 진행 도구 (채팅·화이트보드·미디어·음성 — **이미 구현됨**)

이 스택은 학생앱과 **동일 소켓 프로토콜**(예약 room)로 이미 구축·검증되어 있어, 선생님 모바일은
**같은 이벤트에 붙기만 하면 된다**(신규 백엔드 0). 상담 진행 화면의 핵심 도구가 전부 준비됨:

- **채팅**: 텍스트·이미지 + **읽음 확인·입력 중 표시·미확인 배지** + **무소음 카메라 촬영**(getUserMedia, 셔터음 없음)
- **화이트보드**: 실시간 필기(펜/지우개)·자동저장 + **이미지 첨부/카메라 촬영을 배경으로 → 그 위에 필기**
  (예: 문제를 찍어 그 위에 풀이를 필기, 배경·필기 모두 상대에게 실시간 동기화·영속)
- **음성통화**: 자체 **WebRTC**(P2P 오디오), 시그널링은 게이트웨이 중계. 화이트보드와 같은 room이라
  **필기하며 동시에 음성으로 설명** 가능(수신 자동응답·음소거·종료)
- 게이트웨이 e2e·2-클라이언트 소켓 테스트로 브로드캐스트·영속·시그널링 검증 완료

레이아웃: 태블릿=화이트보드 풀사이즈 + 채팅·통화 사이드, 폰=탭 전환. 필기는 **태블릿+펜**이 1급
시나리오(팜리젝션·펜 압력은 PointerEvent로 구현 완료 `4070f34`; 현재 데모=expo-web canvas, 순수 네이티브는 Skia 후결합).

> 즉 최우선 기능 ②(상담 진행)는 **UI 배치만 남았고 로직·실시간·미디어는 이미 완성** 상태다.

## 7. 벤치마크 차용 (설탭·숨고·크몽·탭 등)

최우선 3종 외 **부가 기능은 검증된 전문가/서비스제공 앱 패턴을 차용**한다.

| 출처 | 차용 패턴 | 우리 화면 적용 |
|---|---|---|
| **숨고(고수)** | 견적 요청 인박스 + "새 의뢰" 실시간 알림 + 빠른수락 | ① 인박스의 상담신청 카드·빠른 수락/거절 |
| **숨고/크몽** | 응답률·평점 뱃지, 프로필 강화가 매칭에 영향 | 마이: 응답률·평점 노출(랭킹 가중과 연동), 프로필 완성도 |
| **크몽(전문가)** | 작업 대화방 + 파일 전달 + 단계(진행중/완료) | ② 상담 진행방(채팅+파일), 상태 전이 UI |
| **탭/카카오 상담** | 대화 목록의 미확인 뱃지·최근 활동 정렬 | ③ 상담·기록 목록 정렬, 미확인 뱃지 |
| **당근/네이버 예약** | 오늘 일정 위젯 + 노쇼/취소 알림 | 오늘 탭, 취소·노쇼 알림 처리 |
| **카카오/토스** | 더블-백 종료·읽음 표시·토스트 UX | 이미 반영(모바일 공통 UX) |

> 원칙: **차용은 UX 패턴 수준**으로, 데이터·정책은 우리 도메인(요금/권한/공개정책)을 따른다.

## 8. 태블릿/폰 반응형 전략

- 단일 코드베이스(RN/expo) + 폭 기반 레이아웃 스위치(이미 학생앱이 expo-web로 반응형).
- **2-pane 컴포넌트**: `<MasterDetail>` — 좌 목록/인박스, 우 상세. `<768`이면 detail을 push 화면으로.
- 상담 진행: 태블릿=채팅+화이트보드 동시, 폰=탭 전환.
- 입력: 태블릿은 외장 키보드/펜 고려(넓은 입력영역), 폰은 하단 시트·큰 터치타깃(44pt+).
- 접근성: 큰 글자·대비, 상태칩 색+라벨 병기(기존 디자인 토큰 재사용).

## 9. 기존 백엔드 재사용 매핑 (신규 최소화)

| 기능 | 상태 | 근거 |
|---|---|---|
| 알림 목록/읽음/실시간 | ✅ 있음 | `/notifications`, 소켓 `notif:new`, 템플릿 |

## 11. 미결정 · 리스크

- **역할 표시 정책**: 선생님이 모바일과 웹을 병행할 때 상태(예약 확정·기록 저장) 충돌 → 서버 상태 단일 소스로 이미 방어. 
- **태블릿 네이티브 필기**: 현재 데모는 expo-web 캔버스. 진짜 네이티브 펜 경험은 RN Skia 등 **별도 네이티브 빌드 과제**(demo 범위 밖).

- **동시 상담**: 세션 독 + 트레이로 스위칭 구현(`39a5565`). 단 세션 전환 시 비활성 세션은 언마운트(재개 시 재연결) — 백그라운드 라이브 유지(동시 음성 다중)는 네이티브 빌드 과제.
