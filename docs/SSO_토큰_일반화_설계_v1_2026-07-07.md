# SSO 토큰 일반화 설계 v1 — 크로스서비스 인증 (W1 D3 ①)

> 2026-07-07 · 구현은 W3(2일). 정본 패턴: `apps/realtime-rooms/src/rooms/token.service.ts`(HS256 수제 JWT + epoch) — 외부 의존 0으로 검증된 구조를 **플랫폼 전역 SSO로 승격**한다.

## 1. 목표·비목표

- **목표:** 플랫폼(janus-platform API) 로그인 1회 → 배치표(정적 티어 HTML)·입결·수시 도구 등 **연계 서비스에 재로그인 없이 진입**. 회원 티어 게이트의 기반.
- **비목표:** OAuth2/OIDC 풀스펙, 외부 IdP 연동(추후 어댑터), 컨설턴트 티어(CF Access — Phase 2, N25).

## 2. 토큰 스펙 (rooms 패턴 승격)

형식: `base64url(header).base64url(payload).HMAC-SHA256(sig)` — HS256, 라이브러리 무의존.

```ts
type SsoToken = {
  sub: string;        // accountId (UUID)
  role: 'student'|'guardian'|'teacher'|'admin'|'hr';
  tier: 'free'|'member'|'paid'|'consultant';   // 티어 게이트의 판정 근거
  aud: string;        // 대상 서비스 id (예: 'baechipyo', 'ipgyeol', 'susi')
  scope: string[];    // 서비스 내 권한 (예: ['view','ingest-score'])
  epoch: number;      // 일괄 폐기 카운터(서비스별) — 증가 시 기존 토큰 전부 무효
  iat: number; exp: number;   // 발급/만료(초). 기본 TTL 15분(진입용, 갱신은 재발급)
};
```

- **시크릿:** `SSO_JWT_SECRET`(ENV, 플랫폼과 검증 게이트만 보유). rooms와 분리 — 시크릿·epoch 네임스페이스 독립.
- **epoch 폐기:** `sso_service.epoch` 컬럼 증가 → 해당 aud의 모든 기존 토큰 즉시 무효(유출 대응). rooms의 room epoch와 동일 메커니즘.

## 3. 서비스 등록 (service registry)

플랫폼 DB 테이블 `sso_service`:

| 컬럼 | 예 | 설명 |
|---|---|---|
| id | `baechipyo` | aud 값 |
| name | 대학 배치표 | 표시명 |
| allowed_scopes | `['view','ingest-score']` | 발급 가능 상한 |
| min_tier | `member` | 이 서비스 진입 최소 티어 |
| epoch | 1 | 일괄 폐기 카운터 |
| redirect_origins | `['https://pages.janus.example']` | 토큰 전달 허용 origin (오픈 리다이렉트 방지) |

신규 서비스 추가 = 행 1개 삽입(코드 변경 없음).

## 4. 발급·검증 흐름

```
[플랫폼 웹/앱]                    [플랫폼 API]                 [정적 티어 페이지(Pages)]
로그인 상태에서 "배치표 열기"
  → POST /api/v1/sso/token {service:'baechipyo'}
        → 로그인 세션 검증, 티어 판정(min_tier 게이트)
        → SsoToken 발급(HS256)                                 
  ← {token, url: 'https://…/baechipyo/?sso=<token>'}
  → window.open(url)  ───────────────────────────────→  ?sso= 파라미터 수신
                                                          → 검증 스니펫이 GET /api/v1/sso/verify?token= 호출
                                                          ← {ok, tier, scope} → 티어 UI 게이트 해제
                                                          → sessionStorage 보관(만료 시 재진입 유도)
```

- **정적 페이지는 시크릿을 가질 수 없으므로** 검증은 플랫폼 API `GET /sso/verify`(CORS: redirect_origins만 허용)로 위임. 회원판 정적 HTML엔 데이터가 이미 임베드되지 않는 전제(티어 빌드에서 물리 분리)라, verify는 **UI 게이트+감사 로그** 역할.
- 서버-투-서버(동적 서비스)는 시크릿 공유로 자체 검증 가능(rooms의 verify 함수 재사용 형태).

## 5. 구현 배치 (W3)

- `packages/sso/`(발급·검증 순수 함수 — rooms TokenService 일반화 복제) + `apps/api/src/modules/sso/`(컨트롤러: token·verify + registry CRUD admin).
- 배치표/입결 **ingest 스니펫**: `?sso=` 파싱 → verify → 티어 게이트 → (scope에 ingest-score 있으면) janus_score 자동 주입과 결합(변환 스펙 문서 참조).
- 테스트: 발급→검증 왕복, 만료·위조·epoch 증가 무효화, min_tier 미달 거부.
