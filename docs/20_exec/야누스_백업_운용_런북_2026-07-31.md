# 야누스 백업 운용 런북 (2026-07-31)

> **왜 필요한가**: 백업은 "돌고 있다"가 아니라 "사고가 났을 때 실제로 되살아난다"로만 검증된다.
> 이 문서는 무엇이 어떤 사고를 막고, 무엇은 못 막는지, 그리고 사람이 지켜야 할 규약을 적는다.
>
> 명령 사용법은 `ops/README.md` 에 있다. 이 문서는 **정책과 판단**을 담당한다.
> 관련 결정: Decision-Register **O199**. 계획서 근거: 실행계획서 **§2-4**.

---

## 1. 위협 모델 — 어떤 사본이 어떤 사고를 막는가

백업을 "몇 벌 있나"로 세면 틀린다. **어떤 사고에 같이 죽는 사본인가**로 세야 한다.

| 사고 | 로컬 덤프<br>(`~/janus-backups`) | R2<br>(restic) | 외장<br>(Time Machine) |
|---|:-:|:-:|:-:|
| 실수로 DROP · 파일 삭제 | ✅ 가장 빠름 | ✅ | ✅ |
| 내장 SSD 사망 | ❌ 같이 죽음 | ✅ | ✅ |
| 맥 도난 · 화재 · 침수 | ❌ | ✅ | ❌ 같은 장소면 같이 잃음 |
| **랜섬웨어 · 자격증명 침해** | ❌ | **❌ (아래 §2)** | **✅ 뽑아 뒀을 때만** |
| **R2 계정 사고**(정지·결제 실패·토큰 유출) | ❌ | ❌ | ✅ |
| 대용량 복구 속도 | 빠름 | 느림(네트워크) | 빠름 |

**핵심**: 로컬 덤프와 원본은 **같은 내장 디스크**에 있다 — 사본 2벌처럼 보이지만 디스크 사망에는 한 몸이다.
외장과 R2 는 서로를 대체하지 않는다. **외장은 오프사이트가 아니고, R2 는 오프라인이 아니다.**

## 2. R2 가 못 막는 것 — 알고 써야 한다

restic 저장소를 **삭제할 수 있는 토큰이 백업 대상 기기 안에** 평문으로 있다
(`~/.config/janus/backup.env`). 따라서:

- 랜섬웨어나 침해가 이 맥에 들어오면 원본을 암호화하면서 **그 파일을 읽어 R2 스냅샷까지 지울 수 있다.**
- restic 은 S3 백엔드에서 **append-only 를 지원하지 않는다**. "오프사이트니까 안전하다"는 성립하지 않는다.

이 시나리오를 막는 것은 **연결돼 있지 않은 매체**뿐이다. 그것이 외장의 존재 이유다.

> 완화책(선택): R2 버킷에 **오브젝트 버전 관리 + 수명주기 보존**을 켜면 삭제 저항이 생긴다.
> 다만 무료 한도(10GB) 소모가 늘고 restic 의 `forget --prune` 과 상호작용이 있으므로,
> 켤 때는 보존 기간을 짧게(예: 30일) 잡고 사용량을 관찰할 것. **본부 확인 필요 항목**이다.

## 3. 외장 디스크 운용 규약

**상시 연결은 방어가 아니다.** 항상 마운트된 백업 디스크는 랜섬웨어가 그대로 암호화한다.
외장의 가치는 **분리돼 있는 시간**에서 나온다.

- **원칙**: 백업이 끝나면 **뽑는다**. 상시 연결로 두지 않는다.
- **주기**: 주 1회(일요일 주간 리뷰와 함께)면 충분하다. 그 사이 공백은 R2 가 메운다.
- **절차**: ① 연결 → ② Time Machine 백업 완료 대기 → ③ 마운트 해제 → ④ 물리적으로 분리
- **보관**: 가능하면 맥과 **다른 방**에 둔다. 같은 책상에 두면 화재·도난에서 같이 잃는다.
- **검증**: 분기 1회, 외장에서 파일 하나를 실제로 복원해 열어 본다(§5 와 같은 원칙 — 복원해 봐야 백업이다).

Time Machine 목적지가 붙으면 실행계획서 **W1 D5** 를 닫을 수 있다.
현재는 `tmutil destinationinfo` 가 `No destinations configured` 다.

## 4. `RESTIC_PASSWORD` 보관 규약 — 유일한 단일 실패점

**이 값을 잃으면 R2 에 백업이 멀쩡히 있어도 전량 영구 소실이다.** restic 은 복구 수단이 없다.

- 원본: `~/.config/janus/backup.env`(권한 600, 저장소 밖)
- **사본은 반드시 비밀번호 관리자에 따로 둔다.** 이 파일 하나에만 두면,
  내장 디스크가 죽는 시나리오에서 **백업은 살아남는데 열쇠가 사라진다.**
- 저장소·이슈·채팅에 절대 붙여넣지 않는다. 백업 파일 자체에만 의존하지 않는다
  (금고 파일이 백업 안에 들어 있어도, 그 백업을 열려면 같은 암호가 필요하다 — 순환이다).

**보관은 검증이 아니다.** 잘못 옮겨 적은 암호는 없는 것보다 나쁘다 — 열쇠가 있다고 믿게
만들어, 정작 사고가 났을 때 대안을 준비할 기회를 빼앗기 때문이다. 사본을 저장한 뒤에는
반드시 한 번 열어 본다:

```bash
./ops/verify-restic-password.sh   # 대화식 — 관리자에서 복사한 값을 붙여넣는다
```

⚠ **`backup.env` 로 여는 것은 이 검증이 아니다.** 그것은 원본을 확인한 것이고, 원본이
동작한다는 사실은 launchd 백업이 매일 증명하고 있다. 남아 있는 명제는 **"사본이 원본과
같은가"** 하나뿐이므로, 사본을 사람이 직접 입력하는 경로가 아니면 검증이 성립하지 않는다.
스크립트가 파일에서 읽힌 값을 `unset` 하는 이유이며, 이것이 §5(검증이 대상을 빗나가는 것)의
같은 함정이다.

## 5. 복원 리허설 — 주기와 방법

§2-4 의 원칙: **"백업은 복원이 검증돼야 백업"**.

- **주기**: 주간 리뷰(일요일)마다 1회. 실행계획서 주간 체크리스트의 '복원 리허설 로그 확인' 항목이 이것이다.
- **반드시 R2 에서 받아서** 한다. 로컬 덤프로 하면 오프사이트를 검증한 것이 아니다.
- **`--no-cache` 를 붙인다.** 안 붙이면 로컬 restic 캐시에서 읽고도 성공한 것처럼 보인다.
- 절차와 명령은 `ops/README.md` 의 "R2 복원 리허설" 절.
- 끝나면 **임시 DB 를 DROP 하고 복원 파일을 삭제한다** — 실데이터다(§1-2).

**대조는 실제 `count(*)` 로 한다.** `n_live_tup` 은 복원 직후 통계가 비어 있어 **거짓 불일치**가 난다.

## 6. 정기 점검

| 주기 | 무엇 | 방법 |
|---|---|---|
| 매일(자동) | 백업 실행 | launchd 03:00 · 로그 `~/janus/backup-offsite.log` |
| 주 1회 | 실행 성공 여부 | `launchctl list \| grep com.janus.backup` — **2번째 열이 마지막 종료코드**(0이어야 정상) |
| 주 1회 | 스냅샷이 실제로 늘었는지 | `restic snapshots --tag janus` — 로그만 보면 놓친다 |
| 주 1회 | 복원 리허설 | §5 |
| 분기 1회 | 데이터 블록 전수 검증 | `restic check --read-data` (매 실행의 구조 검사보다 무겁다) |
| 분기 1회 | 외장 복원 확인 | §3 |
| 분기 1회 + **암호 변경 시마다** | 관리자의 사본이 실제로 여는지 | `./ops/verify-restic-password.sh` (§4) |

**맥이 잠들어 있으면 03:00 실행은 건너뛴다.** `RunAtLoad` 가 로그인 시 1회 보정하므로
스냅샷 시각이 03:00 이 아닐 수 있다 — 이건 실패가 아니다.
다만 **며칠 연속 03:00 실행이 없으면** "밤에 맥이 꺼져 있어 일 1회가 사실상 성립하지 않는" 상태이니
스케줄 시각을 실제 사용 시간대로 옮겨야 한다.

## 7. 지금 구성의 미충족 항목 (2026-07-31 기준)

- **3-2-1 의 '매체 2종' 미충족** — Time Machine 미설정. 사본은 3벌(원본·로컬 덤프·R2)이지만
  앞 둘이 같은 내장 디스크에 있다.
- **랜섬웨어·자격증명 침해에 대한 방어 없음**(§2). 외장 도입 전까지는 이 위험이 열려 있다.
- **`RESTIC_PASSWORD` 사본 여부는 사람이 지켜야 한다**(§4) — 시스템이 강제하지 못한다.
  사본이 *있는지*는 여전히 강제할 수 없지만, 있다면 *맞는지*는 이제 한 명령으로 판정된다
  (`ops/verify-restic-password.sh` — 판별력은 양성·음성 대조로 확인, 2026-07-31).
  **⚠ 아직 그 스크립트를 관리자의 실제 사본으로 돌린 기록은 없다** — 돌리기 전까지
  §4 의 단일 실패점은 열려 있다. 이 줄은 실행 후에 지운다.
