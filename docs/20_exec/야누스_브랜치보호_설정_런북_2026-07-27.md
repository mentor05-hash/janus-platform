# 야누스 — 기본 브랜치 보호 설정 런북 (2026-07-27)

> **왜 필요한가**: 실험·서브 계획으로 하던 작업이 검증 없이 메인에 섞이는 것을 막는다.
>
> ## ⚠ 먼저 — 지금은 이 절차를 쓸 수 없다 (2026-07-27 확인)
>
> **이 저장소는 무료 플랜의 private repo 라 브랜치 보호·룰셋을 쓸 수 없다.**
> 실제로 규칙을 만들어 봤으나 적용되지 않았다:
>
> ```
> GET /repos/…/branches/feat%2Fconsulting-intake
>   protected : False
>   required_status_checks : enforcement_level "off" · contexts []
>
> GET /repos/…/rulesets
>   403 "Upgrade to GitHub Pro or make this repository public to enable this feature."
> ```
>
> **public 전환은 선택지가 아니다** — CLAUDE.md §4(저작권 데이터·PII·시크릿) 위반이다.
>
> → 그래서 지금의 실질 방어선은 **§7 의 pre-push 훅**이다. 아래 §2~§5 절차는
>    **GitHub Pro 로 올린 뒤에** 그대로 쓸 수 있도록 남겨 둔다.
>
> **누가 하는가**: 저장소 소유자만(Pro 이상). **소요**: 5분, 모바일 브라우저 가능.

---

## 1. 지금 상태 — 방어막이 없다

2026-07-27 실측:

| 항목 | 상태 |
|---|---|
| 브랜치 보호 규칙 | **없음** (15개 브랜치 전부 `protected: false`) |
| 기본 브랜치 | `feat/consulting-intake` |
| 기본 브랜치 직접 push | **가능** |
| CI 빨간불 상태 머지 | **가능** |
| force push · 브랜치 삭제 | **가능** |

즉 오늘까지 "CI 초록일 때만 머지"는 **사람의 판단**이었지 시스템 강제가 아니었다.

그리고 구멍이 하나 더 있었다 — 워크플로의 `push` 트리거가 `[main, master]` 만 보고 있어
**기본 브랜치로의 직접 push 는 CI 가 아예 돌지 않았다**. 검증 없이 들어와도 아무도 몰랐다는 뜻이다.
(이 부분은 코드로 고쳤다 — 트리거에 기본 브랜치를 추가하고 `직접 push 감지` 잡을 넣었다.)

## 2. 설정 절차

**GitHub → 저장소 → Settings → Branches → Add branch protection rule**

### 2-1. 대상 브랜치

```
Branch name pattern:  feat/consulting-intake
```

> 기본 브랜치 이름이 바뀌면 이 규칙과 `.github/workflows/ci.yml` 의 `push.branches` 를 **함께** 고쳐야 한다.

### 2-2. 켤 항목

| 체크박스 | 켬 | 이유 |
|---|:-:|---|
| **Require a pull request before merging** | ✅ | 직접 push 를 원천 차단. 실수 유입의 가장 큰 경로다. |
| ↳ Require approvals | ❌ | 1인 저장소라 본인이 본인 PR 을 승인해야 한다 — 번거로움 대비 실익이 낮다. 나중에 사람이 늘면 켠다. |
| **Require status checks to pass before merging** | ✅ | **핵심.** 이걸 켜야 "CI 초록일 때만 머지"가 규칙이 된다. |
| ↳ Require branches to be up to date | ✅ | base 가 움직인 뒤에도 낡은 상태로 머지되는 것을 막는다. 마이그레이션 번호 충돌이 이 경로로 들어온다. |
| **Do not allow bypassing the above settings** | ✅ | 관리자도 우회 못 하게. 켜지 않으면 소유자에겐 규칙이 없는 것과 같다. |
| **Allow force pushes** | ❌ (끔) | 이력 덮어쓰기 차단. |
| **Allow deletions** | ❌ (끔) | 기본 브랜치 삭제 차단. |

### 2-3. 필수 상태 검사로 지정할 잡 — **정확히 이 6개**

검색창에 이름을 넣어 하나씩 추가한다.

```
Lint · Build · Unit
E2E (postgres)
Smoke E2E (ops curl 스크립트)
Web (typecheck · unit)
Mobile (typecheck · expo export)
머지 준비 확인 (미완성 표식)
```

> **`Mobile (typecheck · expo export)` 는 2026-07-30 추가된 잡이다.**
> 그전까지 워크플로에 api·web 만 있어서 **CI 는 모바일이 깨져도 초록이었다** — O185 재편의
> 모바일 변경 3커밋은 로컬 실측이 유일한 증빙이었다. 잡을 만들었어도 **이 목록에 넣지 않으면
> 빨간불까지만이고 머지는 열린다**(§2-3 의 존재 이유가 그것이다).
> `typecheck` 만이 아니라 `expo export` 까지 도는 이유: `tsc` 는 **웹 빌드에서만 드러나는
> 결함**을 못 잡는다. O123 이 그 예다 — `react-native-web` 의 `Alert` 가 빈 함수라 안내
> 22곳이 무음이었는데 타입은 멀쩡했다. 실측 소요 약 2분이고, 가장 긴 `E2E (postgres)`(3~4분)
> 보다 짧아 **총 CI 시간은 늘지 않는다**(병렬).

> ⚠ **`직접 push 감지 (기본 브랜치)` 는 넣지 말 것.**
> 이 잡은 `push` 이벤트에서만 돌고 PR 에서는 `skipped` 로 보고된다(PR #10 에서 실측).
> 즉 **검사로서 아무 의미가 없다**. skip 이 통과로 취급될지 대기로 남을지는
> GitHub 설정·버전에 따라 달라질 수 있으므로, 넣지 않는 편이 안전하다.

## 3. 켠 뒤 무엇이 달라지나

- PR 없이는 기본 브랜치에 아무것도 들어갈 수 없다.
- 6개 검사가 전부 초록이 아니면 머지 버튼이 잠긴다 — **에이전트가 API 로 머지하려 해도 거부된다.**
- 제목에 `[WIP]`·`[실험]`·`[초안]`·`DO NOT MERGE` 가 있거나, 브랜치가 `exp/`·`wip/`·`spike/`·`tmp/` 로 시작하거나, Draft 상태면 `머지 준비 확인` 이 빨간불이라 머지되지 않는다.
  → **서브 계획은 브랜치를 `exp/…` 로 두면 실수로 들어갈 수 없다.**
- 그래도 직접 push 가 일어났다면(규칙을 끄고 밀어넣은 경우 등) `직접 push 감지` 잡이 기본 브랜치에 빨간 X 를 남긴다.

### 표식 규칙 — 한글은 대괄호 형태만

`초안`·`실험` 은 이 제품의 일상 어휘다(“AI 초안 한도”, “실험실 기능”). 맨문자로 잡으면
정상 PR 이 막히므로 **`[초안]`·`[실험]` 처럼 대괄호가 있을 때만** 미완성 표식으로 본다.
표식은 우연히 들어갈 수 없는 모양이어야 한다.

## 4. 부작용 — 알고 켜야 할 것

1. **긴급 수정도 PR 을 거쳐야 한다.** 장애 대응 중 한 줄 고치는 것도 PR → CI(약 4분) → 머지다.
   급하면 Settings 에서 규칙을 잠시 끄고 다시 켜는 방법뿐인데, **그 순간이 가장 위험하므로**
   껐다면 끈 사실과 이유를 남기고 즉시 되돌린다.

2. **오래 열어 둔 PR 이 스스로 빨간불이 된다.** `Require branches to be up to date` 를 켜면
   base 가 움직일 때마다 PR 을 최신화해야 한다. 저자는 아무것도 안 했는데 작업이 생긴다.
   대신 낡은 상태로 머지돼 생기는 사고(마이그레이션 번호 충돌 등)를 막는다.

3. **에이전트도 우회할 수 없다.** 이건 의도한 것이다. 다만 세션이 "머지했다"고 보고하려면
   CI 가 끝날 때까지 기다려야 하므로 세션 시간이 늘어난다.

## 5. 검증 방법

켠 뒤 다음을 확인하면 규칙이 실제로 동작하는지 알 수 있다.

1. 아무 브랜치에서 기본 브랜치로 **직접 push 를 시도** → 거부되어야 한다.
   ```
   git push origin HEAD:feat/consulting-intake
   → remote: error: GH006: Protected branch update failed
   ```
2. PR 을 열고 제목을 `[WIP] 테스트` 로 바꾼다 → `머지 준비 확인` 이 빨간불이 되고 머지 버튼이 잠긴다.
3. 제목에서 `[WIP]` 를 지운다 → 초록으로 바뀌고 머지 버튼이 열린다.

## 6. 관련

- 코드 쪽 조치: `.github/workflows/ci.yml` — `push` 트리거에 기본 브랜치 추가,
  `머지 준비 확인` · `직접 push 감지` 잡 신설.
- 남은 위험: **오래된 브랜치의 은퇴 마이그레이션 번호**.
  `claude/jarvis-homepage-ux-redesign-jirl1u`(0049) · `recolor-lagoon`(0022~) 은
  현재 번호 체계(0001~0106)와 충돌한다 — 되살릴 때 반드시 재번호할 것.
  재번호는 공짜가 아니다: `schema_migrations` 원장이 **파일명**을 키로 쓰므로
  번호를 바꾸면 이미 적용한 DB 가 그 SQL 을 **다시 실행**한다.
  그래서 마이그레이션은 항상 재실행 안전하게(가드 `WHERE` · `IF NOT EXISTS`) 쓴다.

## 7. 지금 실제로 걸려 있는 방어 (무료 플랜)

브랜치 보호를 못 쓰는 동안 아래 3층이 실질 방어선이다.

| 층 | 무엇 | 막는 시점 | 우회 |
|---|---|---|---|
| **pre-push 훅** | `.githooks/pre-push` | **push 전(차단)** | `--no-verify` 로 가능 |
| 머지 준비 확인 | CI 잡 | PR 에서 빨간불 | 규칙이 없으니 무시하고 머지 가능 |
| 직접 push 감지 | CI 잡 | push 후 빨간 X | 사후 |

### pre-push 훅

기본 브랜치(`feat/consulting-intake`·`main`·`master`)로 직접 push 하면 거부한다.

```
$ git push origin HEAD:feat/consulting-intake

  ✗ 'feat/consulting-intake' 로 직접 push 하려 합니다 — 기본 브랜치는 PR 로만 들어와야 합니다.
```

**연결은 자동이다** — `ops/session-deps.sh` 가 세션 시작마다 `git config core.hooksPath .githooks`
를 설정한다. git 설정은 클론에 따라오지 않으므로 매번 연결해야 한다.

수동으로 켜려면:

```bash
git config core.hooksPath .githooks
```

대상 브랜치는 `JANUS_PROTECTED_BRANCHES` 환경변수로 덮어쓸 수 있다.

### 한계 — 알고 쓸 것

`--no-verify` 로 우회된다. **의도적 우회는 못 막고, 실수를 막는다.**
서버측 강제가 필요하면 GitHub Pro 로 올린 뒤 §2 를 실행하라 —
그때도 훅은 그대로 두면 되고, 두 층이 겹쳐 손해가 없다.
