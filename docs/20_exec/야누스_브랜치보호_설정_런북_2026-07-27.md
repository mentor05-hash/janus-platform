## 2. 설정 절차

**GitHub → 저장소 → Settings → Branches → Add branch protection rule**

### 2-1. 대상 브랜치

규칙은 **두 개**다 — 각각 따로 만든다.

```
Branch name pattern:  feat/consulting-intake     ← 기본 브랜치
Branch name pattern:  master                     ← 레거시 (2026-07-30 추가)
```

> 기본 브랜치 이름이 바뀌면 이 규칙과 `.github/workflows/ci.yml` 의 `push.branches` 를 **함께** 고쳐야 한다.

> `master` 는 기본 브랜치보다 **459 커밋 뒤처져 있고 master 에만 있는 커밋은 0 개**다(전부 기본 브랜치에 포함). 죽은 브랜치지만 force push · 삭제로 이력을 잃을 수 있어 **기본 브랜치와 같은 표준**을 걸었다. 워크플로의 `push.branches` 에 `master` 가 있고 `pull_request` 에는 브랜치 필터가 없어서 **검사 6개가 master 에서도 정상으로 돈다** — 검사가 돌지 않는 브랜치에 required checks 를 걸면 영원히 pending 으로 남아 아무것도 못 들어간다. 새 브랜치에 보호를 걸 때 반드시 먼저 확인할 것.

### 2-2. 켤 항목

| 체크박스 | 런북 지시 | 실측 (2026-07-30) | 이유 |
|---|:-:|:-:|---|
| **Require a pull request before merging** | ✅ | ✅ 일치 | 직접 push 를 원천 차단. 실수 유입의 가장 큰 경로다. |
| ↳ Require approvals | ❌ | ❌ 일치 | 1인 저장소라 본인이 본인 PR 을 승인해야 한다 — 번거로움 대비 실익이 낮다. 나중에 사람이 늘면 켠다. |
| **Require status checks to pass before merging** | ✅ | ✅ 일치 | **핵심.** 이걸 켜야 "CI 초록일 때만 머지"가 규칙이 된다. |
| ↳ Require branches to be up to date | ✅ | ✅ `strict:true` | base 가 움직인 뒤에도 낡은 상태로 머지되는 것을 막는다. 마이그레이션 번호 충돌이 이 경로로 들어온다. |
| **Do not allow bypassing the above settings** | ✅ | ✅ 일치 | 관리자도 우회 못 하게. 켜지 않으면 소유자에겐 규칙이 없는 것과 같다. |
| **Allow force pushes** | ❌ (끔) | ❌ 일치 | 이력 덮어쓰기 차단. |
| **Allow deletions** | ❌ (끔) | ❌ 일치 | 기본 브랜치 삭제 차단. |

> ⚠ **켤 때 밟는 함정 — `Require approvals` 가 딸려 켜진다** (2026-07-30 실측):
>
> `Require a pull request before merging` 을 켜는 순간, 예전에 껐을 때 남아 있던
> `required_approving_review_count: 1` 이 **되살아나 함께 적용된다.** 그 결과:
>
> - PR 이 `reviewDecision: REVIEW_REQUIRED` · `mergeStateStatus: BLOCKED` 가 된다.
> - GitHub 은 **본인 PR 을 본인이 승인하는 것을 금지**하고, 조직 시트가 1개라 승인할 사람이 없다.
> - `Do not allow bypassing` 까지 켜져 있으면 소유자 우회도 막혀 **완전히 잠긴다.**
>
> 그래서 두 개를 켠 뒤 **`Require approvals` 를 다시 꺼야** 위 표대로가 된다.
> 확인은 `required_approving_review_count` 가 0 인지로 하라 — GraphQL 의
> `requiresApprovingReviews` 는 이름과 달리 'PR 필수'를 뜻해서 승인수가 0 이어도 true 다.

### 2-3. 필수 상태 검사로 지정할 잡 — **정확히 이 6개**

검색창에 이름을 넣어 하나씩 추가한다.

```
Lint · Build · Unit
E2E (postgres)
Smoke E2E (ops curl 스크립트)
Web (typecheck · unit)
Mobile (typecheck · expo export)
머지 준비 확인 (미완성 표식)
```

> **`Mobile (typecheck · expo export)` 는 2026-07-30 추가된 잡이다.**
> 그전까지 워크플로에 api·web 만 있어서 **CI 는 모바일이 깨져도 초록이었다** — O185 재편의
> 모바일 변경 3커밋은 로컬 실측이 유일한 증빙이었다. 잡을 만들었어도 **이 목록에 넣지 않으면
> 빨간불까지만이고 머지는 열린다**(§2-3 의 존재 이유가 그것이다).
> `typecheck` 만이 아니라 `expo export` 까지 도는 이유: `tsc` 는 **웹 빌드에서만 드러나는
> 결함**을 못 잡는다. O123 이 그 예다 — `react-native-web` 의 `Alert` 가 빈 함수라 안내
> 22곳이 무음이었는데 타입은 멀쩡했다. 실측 소요 약 2분이고, 가장 긴 `E2E (postgres)`(3~4분)
> 보다 짧아 **총 CI 시간은 늘지 않는다**(병렬).

> ⚠ **`직접 push 감지 (기본 브랜치)` 는 넣지 말 것.**
> 이 잡은 `push` 이벤트에서만 돌고 PR 에서는 `skipped` 로 보고된다(PR #10 에서 실측).
> 즉 **검사로서 아무 의미가 없다**. skip 이 통과로 취급될지 대기로 남을지는
> GitHub 설정·버전에 따라 달라질 수 있으므로, 넣지 않는 편이 안전하다.

## 3. 켠 뒤 무엇이 달라지나

- PR 없이는 기본 브랜치에 아무것도 들어갈 수 없다.
- 6개 검사가 전부 초록이 아니면 머지 버튼이 잠긴다 — **에이전트가 API 로 머지하려 해도 거부된다.**
- 제목에 `[WIP]`·`[실험]`·`[초안]`·`DO NOT MERGE` 가 있거나, 브랜치가 `exp/`·`wip/`·`spike/`·`tmp/` 로 시작하거나, Draft 상태면 `머지 준비 확인` 이 빨간불이라 머지되지 않는다.
  → **서브 계획은 브랜치를 `exp/…` 로 두면 실수로 들어갈 수 없다.**
- 그래도 직접 push 가 일어났다면(규칙을 끄고 밀어넣은 경우 등) `직접 push 감지` 잡이 기본 브랜치에 빨간 X 를 남긴다.

> 위 두 줄은 §2-2 의 ✅ 두 개가 켜져 있어야 성립한다. 2026-07-30 부터 둘 다 켜져 있어
> **소유자 토큰으로도 우회되지 않는다** — 에이전트가 쓰는 토큰이 바로 그것이라 이 차이가 중요하다.
> 둘 중 하나라도 꺼지면 이 문단은 즉시 거짓이 된다. 규칙을 손댄 뒤에는 §2-2 의 실측 열을 다시 확인하라.

`초안`·`실험` 은 이 제품의 일상 어휘다(“AI 초안 한도”, “실험실 기능”). 맨문자로 잡으면

## 4. 부작용 — 알고 켜야 할 것

1. **긴급 수정도 PR 을 거쳐야 한다.** 장애 대응 중 한 줄 고치는 것도 PR → CI(약 4분) → 머지다.
   급하면 Settings 에서 규칙을 잠시 끄고 다시 켜는 방법뿐인데, **그 순간이 가장 위험하므로**
   껐다면 끈 사실과 이유를 남기고 즉시 되돌린다.

2. **오래 열어 둔 PR 이 스스로 빨간불이 된다.** `Require branches to be up to date` 를 켜면
   base 가 움직일 때마다 PR 을 최신화해야 한다. 저자는 아무것도 안 했는데 작업이 생긴다.
   대신 낡은 상태로 머지돼 생기는 사고(마이그레이션 번호 충돌 등)를 막는다.

3. **에이전트도 우회할 수 없다.** 이건 의도한 것이다. 다만 세션이 "머지했다"고 보고하려면
   CI 가 끝날 때까지 기다려야 하므로 세션 시간이 늘어난다.

## 5. 검증 방법

켠 뒤 다음을 확인하면 규칙이 실제로 동작하는지 알 수 있다.

1. 아무 브랜치에서 기본 브랜치로 **직접 push 를 시도** → 거부되어야 한다.
   ```
   git push origin HEAD:feat/consulting-intake
   → remote: error: GH006: Protected branch update failed
   ```
2. PR 을 열고 제목을 `[WIP] 테스트` 로 바꾼다 → `머지 준비 확인` 이 빨간불이 되고 머지 버튼이 잠긴다.
3. 제목에서 `[WIP]` 를 지운다 → 초록으로 바뀌고 머지 버튼이 열린다.

> ⚠ **1번은 실측하지 않았다.** 기본 브랜치로 실제 push 를 시도하는 시험이라
> 거부를 기대하고 돌리기에는 위험이 크다 — 막지 못하면 기본 브랜치가 오염된다.
> 2·3번은 PR 에서 제목만 바꿔 보면 되므로 위험이 없다.

## 6. 관련

- 코드 쪽 조치: `.github/workflows/ci.yml` — `push` 트리거에 기본 브랜치 추가,
  `머지 준비 확인` · `직접 push 감지` 잡 신설.
- 남은 위험: **오래된 브랜치의 은퇴 마이그레이션 번호**.
  `claude/jarvis-homepage-ux-redesign-jirl1u`(0049) · `recolor-lagoon`(0022~) 은
  현재 번호 체계(0001~0106)와 충돌한다 — 되살릴 때 반드시 재번호할 것.
  재번호는 공짜가 아니다: `schema_migrations` 원장이 **파일명**을 키로 쓰므로
  번호를 바꾸면 이미 적용한 DB 가 그 SQL 을 **다시 실행**한다.
  그래서 마이그레이션은 항상 재실행 안전하게(가드 `WHERE` · `IF NOT EXISTS`) 쓴다.
- ⚠ **소유자 판정**: `git remote -v` 는 아직 `mentor05-hash/janus-platform` 를 가리킨다
  (2026-07-30 조직 이전 뒤에도 GitHub 리다이렉트로 push·fetch 는 정상 동작한다).
  소유자·발효 상태는 `gh repo view` · `git ls-remote` 로 원격을 직접 조회해 판정한다 —
  remote URL 은 근거가 아니다.
- 조직 rulesets 는 토큰에 `admin:org` 스코프가 없어 확인하지 못했다(repo rulesets 는 0건이라
  classic 브랜치 보호가 유일한 활성 계층이다). 필요하면 `gh auth refresh -h github.com -s admin:org`.

## 7. 여러 층으로 막는다 — 훅 + 서버 쪽 강제

2026-07-30 이후로는 아래 4층이 겹쳐 있다. 훅은 그대로 두는 것이 맞다 — 마지막 '한계' 항을 보라.

| 층 | 무엇 | 막는 시점 | 우회 |
|---|---|---|---|
| **pre-push 훅** | `.githooks/pre-push` | **push 전(차단)** | `--no-verify` 로 가능 |
| 머지 준비 확인 | CI 잡 | PR 에서 빨간불 | **required check 라 머지 차단** |
| 직접 push 감지 | CI 잡 | push 후 빨간 X | 사후 |
| **required checks 6개** | 브랜치 보호 | **머지 버튼 잠김** | 없음(`enforce_admins:true`) |

### pre-push 훅

기본 브랜치(`feat/consulting-intake`·`main`·`master`)로 직접 push 하면 거부한다.

```
$ git push origin HEAD:feat/consulting-intake

  ✗ 'feat/consulting-intake' 로 직접 push 하려 합니다 — 기본 브랜치는 PR 로만 들어와야 합니다.
```

**연결은 자동이다** — `ops/session-deps.sh` 가 세션 시작마다 `git config core.hooksPath .githooks`
를 설정한다. git 설정은 클론에 따라오지 않으므로 매번 연결해야 한다.

수동으로 켜려면:

```bash
git config core.hooksPath .githooks
```

대상 브랜치는 `JANUS_PROTECTED_BRANCHES` 환경변수로 덮어쓸 수 있다.

### 한계 — 알고 쓸 것

`--no-verify` 로 우회된다. **의도적 우회는 못 막고, 실수를 막는다.**
서버 쪽 강제는 2026-07-30 에 켜졌으므로(맨 위 박스) 훅은 이제 **두 번째 층**이다 —
그대로 두면 되고, 두 층이 겹쳐 손해가 없다. 훅은 push 전에 막아 CI 4분을 아낀다.
