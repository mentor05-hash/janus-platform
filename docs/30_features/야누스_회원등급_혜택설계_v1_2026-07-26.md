## 1. 왜 이 설계가 필요했나

O50(가격 확정) 과정에서 **크레딧으로는 상위 등급을 유리하게 만들 수 없다**는 것이 드러났다.

배분 원가 = 소비 크레딧 × 0.5 × 60% 이므로 **크레딧에 선형**이다. 상위 등급에 볼륨 할인을 주려고 부여를 늘리면 마진이 그만큼 그대로 깎인다. `ops/pricing-sim.mjs --ladder-probe` 실측:

| VIP 부여 | Premium 대비 우위 | 공헌이익률 | 스트레스(소멸 0%) |
|---|---|---|---|
| **380,000 (O50 확정)** | **+7.5%** | **30.9%** | **19.3%** |
| 470,000 | +25.2% | 15.3% | 0.9% ← 사실상 원가 |
| 500,000 | +29.7% | 10.1% | **−5.2%** ← 적자 |

즉 **크레딧 축의 우위는 +7.5% 에서 끝났다.** VIP 가 Premium 대비 갖는 나머지 차별화는 다른 축에서 만들어야 한다. 그게 이 문서다.

## 2. 설계 원칙 — 어떤 축을 혜택으로 쓸 수 있나

원칙은 하나다: **원가가 등급에 비례하지 않는 축만 쓴다.** 세 종류로 나뉜다.

| 종류 | 성격 | 예 |
|---|---|---|
| ① 순서 | 총량을 늘리지 않는다. 원가 **0** | 답변 큐 우선권 |
| ② 정적 접근권 | 한계원가 **≈ 0** | 배치표·입결 산출물 티어 |
| ③ 상한이 명확한 소량 원가 | 등급당 **수백 원** | AI 진단 리포트 발급 횟수 |

②를 쓸 수 있는 것이 야누스의 구조적 이점이다 — 배치표·입결은 정적 산출물이라 한 명이 더 봐도 원가가 늘지 않는다(단품 공헌이익률 97%, 워크시트 §6).

## 3. 발견 — "우선 매칭"은 현 구조에서 정의되지 않는다

백로그 B218 은 혜택 후보로 "**우선 매칭** · 유료 배치표 접근 · 리포트"를 적었다. 그런데 코드를 열어 보면 **우선 매칭은 성립하지 않는다.**

- `MatchingService.autoMatch()` 는 학생별로 **7일 내 첫 가용 슬롯**을 독립적으로 찾는다(first-fit).
- 학생끼리 줄을 서는 **공유 큐가 없다.** 경합이 없으므로 "먼저 처리"할 대상이 없다.
- `booking` 의 `route: 'priority'` 는 이름이 비슷하지만 다른 것이다 — **선생님이 취소했을 때 대체 선생님을 자동배정**하는 경로다(학생 간 경합이 아님).

그럼 플랫폼에서 **학생끼리 실제로 경합하는 지점**은 어디인가. 하나뿐이다:

> **Q&A 답변 큐.** 선생님이 공개 질문 목록을 보고 위에서부터 `claim()` 한다(선착순). **목록 순서가 곧 응답 속도**다.

그래서 "우선 매칭"을 **"우선 답변"으로 재정의**했다. 매칭 쪽은 대신 **탐색 지평 확대**(7 → 14 → 21일)로 바꿨다 — 우선권은 아니지만 "자리를 찾을 확률"이라는 실질 가치가 있고 원가는 0이다.

### 부수 발견: `membership_grade.priority` 는 죽은 필드였다

시드에 0/1/2/3 이 들어가 있지만 **코드 어디서도 읽지 않는다**. 이번에도 이 컬럼을 쓰지 않았다 — `priority` 는 "등급 표시 정렬 순서"라는 원래 의미가 있어 큐 가중치로 재사용하면 두 의미가 섞인다. 큐 가중치는 정책값(`grade_benefits_policy`)에 뒀다.

## 4. 혜택 매트릭스

tier 는 `membership_grade.tier` (1=Basic · 2=Standard · 3=Premium · 4=VIP).

| 축 | Basic | Standard | Premium | VIP | 원가 |
|---|---|---|---|---|---|
| `qnaQueueWeight` Q&A 답변 큐 가중치 | 0 | 0 | 1 | **2** | 0 |
| ~~`concurrentBookings` 동시 보유 예약~~ | ~~1~~ | ~~2~~ | ~~4~~ | ~~무제한~~ | — |
| ↳ **정정(B222)**: 혜택 축이 아니라 **운영 통제**로 재분류. 전 등급 기본 무제한 | 0 | 0 | 0 | 0 | 0 |
| `placementTier` 배치표 티어 | member | member | paid | **paid** | ≈0 |
| `aiReportsPerMonth` AI 리포트 월 발급 | 0 | 1 | 3 | **6** | 402원 |
| `matchHorizonDays` 매칭 탐색 지평 | 7 | 7 | 14 | **21** | 0 |

등급이 없는 계정(비구독·외부생)은 `NO_GRADE_BENEFIT` — 배치표는 **무료 티어만**, 나머지는 Basic 과 동일. 조회가 실패하면 항상 이 값으로 떨어진다(**닫힌 쪽으로 실패**).

### 왜 Basic 도 배치표 `member` 인가

기획서 v2 가 "**회원 = 무료 가입(리드)**"으로 설계했다. 가입만 해도 회원 티어를 열어 주는 것이 리드 확보 경로이므로, 여기서 조이면 퍼널이 막힌다. 유료 경계는 `member` → `paid` 사이에 둔다.

### VIP 의 실질 우위

크레딧 +7.5% 에 더해 — 큐 가중치 2배 · 리포트 2배 · 탐색 지평 3주. 이 중 **원가가 붙는 것은 리포트뿐이고 402원**이다(공헌이익 46,106원의 0.9%).
(예약 상한은 B222 로 운영 통제로 재분류돼 우위 항목에서 빠졌다.)

## 5. Q&A 큐 우선권이 기아를 만들지 않게 하는 장치

가중치만으로 정렬하면 Basic 학생 질문이 상위 등급에 계속 밀려 **영구히 안 풀린다**. 유료 우선권이 무료 사용자를 방치하는 구조가 되면 서비스 신뢰가 깨진다.

그래서 **48시간이 지난 질문은 등급을 무시하고 맨 앞으로** 보낸다.

정렬 규칙(우선순위 순):

1. **48h 초과 미답** — 등급 무시, **오래된 것부터**
2. 그 외 — **등급 가중치 높은 것부터**, 같으면 최신부터(기존 동작 유지)

실측된 정렬 결과:

```
입력: VIP-신규(1h) · Basic-신규(2h) · Premium-어제(20h) · Basic-3일전(72h) · VIP-4일전(96h)
출력: VIP-4일전 → Basic-3일전 → VIP-신규 → Premium-어제 → Basic-신규
      └── 48h 초과분 먼저(오래된 순) ──┘  └──── 나머지는 등급순 ────┘
```

**48시간이라는 값은 임의가 아니다.** 급여의 48h 미답 보상(`payroll.staleAnswerBonus`, T5c)과 같은 값으로 맞췄다 — 보상이 걸리는 시점과 큐가 끌어올리는 시점이 어긋나면 두 정책이 서로 싸운다.

## 6. 구현 상태 — 무엇이 배선됐고 무엇이 남았나

| 축 | 상태 | 비고 |
|---|---|---|
| `qnaQueueWeight` | ✅ **배선 완료** | `QnaService.listPosts()` 교사 브랜치. 앱 단 정렬(정책값이 단일 소스라 SQL 정렬 불가) |
| `matchHorizonDays` | ✅ **배선 완료** | `MatchingService.autoMatch()` — `HORIZON_DAYS` 상수를 등급값으로 대체(폴백 7일) |
| `placementTier` | 🟡 **정의만** | **B003(SSO 토큰 발급, W3) 선행 필요.** 등급→티어 매핑은 확정됐으므로 B003 은 이 값을 읽기만 하면 된다 |
| ~~`concurrentBookings`~~ | ✅ **규칙 확정(B222)** | 혜택 축에서 내리고 운영 통제로 재분류. `effectiveConcurrentBookings()` 가 유효값 확정 · `GET /me/benefits` 노출. 기본 전 등급 무제한이라 예약 생성 차단 배선은 값을 켤 때 함께 |
| `aiReportsPerMonth` | ✅ **집행 경로 완성(B221)** | `SubjectQuota`(사용자·월) + `AiEntitlementService.consume()`. **소비처(리포트 기능)는 아직 없다** — 만들 때 이 게이트를 거쳐야 한다 |

배선한 2개는 원가 0이고 자체 완결적이라 지금 넣었다. 나머지 3개 중 2개는 B221/B222 로 정리했고(§7), `placementTier` 만 B003 대기다.

## 7. 미해결 상호작용 — 배선 전에 반드시 정할 것

### ① 혜택(권리)과 B008 비용 상한(보호)이 조율되지 않았다 → 🟢 **해소 (2026-07-26, B221)**

> **해소 방식**: 아래 3안 중 **①(사용자·월 쿼터 별도 + 전역 상한은 그 합보다 높게 유지)** 을 택하되,
> 거기에 **3층 정합 불변식**을 더했다 — 감당 못 하는 양의 권리는 애초에 팔 수 없다.
> 상세: `docs/30_features/야누스_AI사용량_3층정책_v1_2026-07-26.md`
> 부수 수정 2건(라이브 결함): 신고 AI 검토의 사용자별 한도 부재 · 비용 상한이 신고 접수를 막던 순서.

아래는 발견 당시의 기록이다.

`aiReportsPerMonth` 는 "이만큼 쓸 수 있다"는 **권리**이고, B008 의 `LLM_DAILY_LIMIT_CONSULTING=60/일` 은 "이 이상 못 쓴다"는 **전역 보호**다. 둘은 서로를 모른다.

실측한 경계:

| 조건 | 일 리포트 수 | B008 상한 60 |
|---|---|---|
| VIP 100명 × 기본값 6건/월 | 20.0건 | 여유 |
| VIP 100명 × **안전선 20건/월** | 66.7건 | **초과** |

즉 안전선까지 열면 유료 사용자가 **"오늘 AI 사용량을 모두 사용했습니다"** 를 보게 된다 — 돈을 받고 판 권리를 전역 상한이 거절하는 상황이고, 이는 권리를 안 주는 것보다 나쁘다. 이 사실을 spec 으로 고정해 뒀다(`안전선까지 열어도…` 케이스).

**해소 방향(택1, 배선 전 결정):**

1. 사용자·월 단위 쿼터를 별도로 만들고, 전역 상한은 그 합보다 높게 유지 — 가장 정직하지만 구현이 가장 크다
2. 혜택을 올릴 때 `LLM_DAILY_LIMIT_CONSULTING` 을 함께 올리는 것을 **운영 절차로 강제**(관리 화면에 경고 표시)
3. 안전선을 B008 과 정합되는 값으로 낮춘다(VIP 100명 기준 18건/월 이하)

### ② 동시 예약 상한이 두 곳에 생긴다 → 🟢 **해소 (2026-07-26, B222)**

> **결정**: 소유자는 센터, 등급값은 선택적 추가 제한, **더 엄격한 쪽이 이긴다**. 기본 전 등급 무제한.
> `effectiveConcurrentBookings()` 가 유효값을 확정하고 `GET /me/benefits` 가 그 값만 노출한다
> (등급값을 그대로 보여 주면 "VIP 무제한"이 센터 한도에 막혀 거짓이 된다).
> 조사 중 확인: `limit_policy.reservation_limit` 도 **집행되지 않는 죽은 필드**였다 — 충돌이 아니라 둘 다 미집행 상태였다.

아래는 발견 당시의 기록이다.

`limit_policy.reservation_limit`(센터 단위, 현재 전부 `null`=무제한)과 `concurrentBookings`(등급 단위)가 같은 것을 제한한다. **더 엄격한 쪽을 적용**하는 것이 안전하지만(센터가 운영상 조인 값을 등급 혜택이 뚫으면 안 된다), 그러면 "VIP 무제한"이 센터 한도에 막혀 혜택 광고와 실제가 달라진다. 배선 전에 문서로 정할 것.

### ③ 큐 정렬이 앱 단이라 목록이 커지면 비용이 든다

정책값이 단일 소스이므로 SQL 로 정렬할 수 없어 전체를 받아 정렬한다. 대상은 **미답 공개 질문**이라 자연히 작지만, 교사 브랜치에는 `take` 가 없다(기존에도 없었다). 미답이 수천 건 쌓이는 상황이 오면 `take` + 커서 페이징이 필요하다.

## 8. 운영 — 값 바꾸기

```bash
GET  /api/v1/admin/grade-benefits          # 현재 정책(기본값 ← system_setting override)
PUT  /api/v1/admin/grade-benefits          # 부분 변경. 본사(HQ) 관리자 한정, 감사 로그 필수
     { "4": { "aiReportsPerMonth": 8 } }   # 예: VIP 리포트만 8건으로
```

- **배포 불필요.** 해석 순서는 다른 정책과 동일(코드 기본값 ← `system_setting('grade_benefits_policy')`).
- **부분 저장값은 기본값으로 메꾼다** — 한 필드만 저장해도 나머지 혜택이 0 으로 유실되지 않는다.
- **정의되지 않은 등급은 무시한다** — 오타(`"9"`)로 새 등급이 생기지 않는다.
- **안전선 초과는 서버가 거부한다**: 큐 가중치 ≤ 3 · 리포트 ≤ 20/월 · 탐색 지평 ≤ 30일 · 동시 예약 ≤ 50.
  큐 가중치 상한을 두는 이유는 §5 의 기아 문제다(48h 장치와 이중 방어).
- 변경 이력은 감사 로그(`grade_benefits.update`, before/after)에 남는다 — 과금 상품의 구성이므로 분쟁 시 "그때 무엇을 팔았나"의 근거가 된다.
