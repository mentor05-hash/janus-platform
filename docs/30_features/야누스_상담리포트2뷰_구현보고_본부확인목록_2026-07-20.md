# 상담 요약 리포트 2뷰(학생용/학부모용) — 구현 보고 + 본부 확인 필요 목록

> 작성 2026-07-20 · 근거 브리핑: 「야누스_상담요약리포트_학부모수신·2뷰발송_개발브리핑_v1」 · 코드 우선 확인 결과 반영.
> 지위: 브리핑 §8(미결)은 **구현하지 않고 이 목록으로 반환**. §10 PR-1~PR-4 구현 완료(오디오 플래그와 무관하게 동작), PR-5 검증·감사 포함.

## 0. 착수 전 확인 결과 — "이미 있는가?" (사용자 질문 직접 답변)

- **오디오 요약 파이프라인: 있음.** `consult_report`(booking당 1, `transcript_id` nullable, body={covered,diagnosis,next_actions}) + `ConsultReportService`(egress→STT→LLM→검수→발송) + 웹 검수/열람 UI. 단 **단일 뷰**이고 오디오 동의 플래그(consult_recording.sttEnabled, 기본 OFF)에 종속.
- **보드 스냅샷+상담사 메모 폴백: 원천 데이터·서비스는 있음.** `consultation_note`(core_summary·homework·future_dir=공개 / **memo=내부** / guardian_visible 게이트) + `ConsultationService`. 단 이를 요약 리포트로 흡수하는 **폴백 연결(`getSummarySource`)은 없었음** → 이번에 신설.
- **결론:** 오디오 요약은 존재하나 오디오 종속. 브리핑의 "핵심 디커플링"을 위해 **메모 폴백 원천 + 2뷰 레이어**를 이번에 구현 — 오디오 OFF 상태에서도 상담 기록(final)만 있으면 2뷰가 만들어진다(E2E 검증).

## 1. 브리핑 §3 표와 코드의 차이 (코드 우선 — 반환)

| 브리핑 가정 | 실제 코드 | 처리 |
|---|---|---|
| `summary_reports` | 실제 테이블명 **`consult_report`** (transcript_id nullable) | 이 위에 뷰 별테이블 얹음(원 무변경) |
| guardian 계정·연결 "미결(§8)" | **이미 존재** — `guardian`·`guardian_student_link`·`consent_grant` + `GuardianReportService`(주간 집계) | 링크를 재사용해 학부모 열람 구현(신규 계정체계 불요) |
| `report_views`/`report_deliveries` 2테이블 | 없음 | **1테이블 `consult_report_view`로 병합**(audience별 body+검수+공유+열람 상태) — 필드명 코드 컨벤션 반영, 병합은 설계 단순화 |
| funnel_event | 존재 | generated/approved/opened{audience}/shared_to_guardian 서버 적재 |

## 2. 구현 요약 (PR-1~PR-4)

- **PR-1 원천 추상화+2뷰+가드레일**: `getSummarySource(bookingId)`=오디오 유래 요약 우선, 없으면 메모 폴백(⚠**내부 memo 제외**, 공개 필드만). `LlmProvider.consultReportViews()`(claude+mock) — 가드레일: 원천에 없는 사실 금지·합격 단정 금지·**가격/상품 단정 금지**("권장"까지)·식별정보 금지. mig `0081_consult_report_views`.
- **PR-2 검수 UI**: 선생님 검수함(`/media/reports/mine`)에 리포트 없는 상담도 상담기록(final)만 있으면 `status='note'`로 노출(폴백 진입점). 웹 TeacherReportsPage에서 학생/학부모 뷰 나란히 편집→승인→발송.
- **PR-3 학생 열람+계측**: 학생 계정에 2뷰 모두 노출(sent만), 학생 뷰 첫 열람 스탬프+`opened{student}` 계측. 웹 StudentReportsPage 2탭.
- **PR-4 guardian 훅(OFF)+공유**: 학생 주도 `share-guardian` → 연결된 학부모가 공유분만 열람(`/media/reports/guardian/:studentId[/:bookingId]`, `opened{guardian}` 계측). **직접 push는 훅만 — `maybePushGuardian` 플래그 guardianPush 기본 false → no-op.** 웹 GuardianConsultReportsPage(내비 '상담 리포트') 신설.
- **PR-5 검증·감사**: `media_access_log`에 report_view read 기록. `ops/consult-report-views-e2e.sh`(run-all 편입) — 폴백/오디오 양 원천·**내부 메모 미유입**·guardian 접근통제(403) 실측 통과.

## 3. ⛔ 금지선 준수 확인

- 미성년 자녀 데이터 학부모 **직접 push 미활성**(훅만, 플래그 OFF) — 기본 전달=계정 내 열람 + 학생 주도 공유.
- 리포트 내 **가격·상품 단정 없음**(LLM 가드레일 + 웹 라벨 "권장까지").
- **janus_score/격차리포트 규약 무변경**(읽지도 않음 — v1은 원천 요약만 사용).
- SSO·tier·"잇올" 명칭·실데이터/시크릿 무변경. consult_report 원 스키마 무변경(뷰 별테이블).

## 4. 본부 확인 필요 (§8 — 구현 안 함, 결정 대기)

1. **guardian 등록·본인확인·동의 방식**(미성년 데이터 공유의 법적 근거) — 본부/법무. *현재: 계정 내 열람 + 학생 주도 공유로만 제한, 직접 push OFF.*
2. **학부모 열람 경로 확정** — 현재 "연결된 guardian 계정이 공유분 열람" 방식으로 구현(기존 guardian_student_link 재사용). 별도 공유 링크/학생 대리 방식 채택 시 조정 필요.
3. **"다음 액션"의 가격·상품 노출 여부** — 현재 ⛔ 비노출("권장"까지). 노출 결정 시 별도 정책+가드레일 완화 필요.
4. **직접 push 채널(알림톡/이메일) 도입·연동** — 도입 확정 시 `maybePushGuardian` guardianPush 플래그 ON + NotificationProvider 배선(현재 no-op 훅).
5. **guardian_view 식별정보 노출 범위** — 현재 원천 요약만(성적·학교 등 미포함). 최소노출 구체선 확정 필요.
6. **(추가 관찰) consultation_note.guardian_visible=false 인 상담**의 2뷰 생성 정책 — 현재는 생성하되 발송·공유는 선생님/학생이 통제. 이 플래그를 guardian 뷰 생성 차단으로 연동할지 결정 필요.

## 5. 잔여(백로그 — 외부·본부 무관, 후속 구현 가능)

- **모바일 2뷰 파리티**: 현재 모바일 ReportsScreen은 기존 단일 뷰(consult_report.body) 열람 유지 — 웹 2뷰/공유 파리티는 후속.
- 오디오 유래 리포트가 이미 있고 폴백 draft가 겹칠 때의 재생성 UX(현재 최신 원천 우선, 선생님 재생성 버튼 제공).
