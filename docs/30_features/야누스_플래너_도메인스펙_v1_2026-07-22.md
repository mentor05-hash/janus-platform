## 0. 금지 사항 (스키마 레벨에서 강제)

- `cohort`·빌보드 어디에도 성적·등급·배치표 결과 필드 금지(D-006). 필드 추가 시도 자체가 스펙 위반.
- 크레딧·보상액 필드 금지(D-004 경제 동결) — 보상은 배지 코드 문자열까지만.
- 실명·연락처는 도메인 밖(계정 모듈 소관). cohort 멤버는 `anon_id`+`nickname`만.

## 1. 스키마 6종 (필드 레벨)

```js
// 1) journey — 여정 온보딩 (기획서 §1)
journey {
  user_id: string,
  driver: 'self'|'guardian'|'co',          // 운전자
  age_band: 'elem'|'middle'|'high'|'adult',// 초등이하/중등/고등·N수/성인
  goal: { type:'exam'|'habit'|'custom', label:string, d_day?:ISODate },
  intensity: 1|2|3|4|5,                    // 친구~서약(§2). v1 엔진은 1~3만 사용
  consent: { guardian:boolean, notify_guardian:boolean }  // 미성년 필수
}

// 2) availability — 가용 시간·환경 (기획서 §3)
availability {
  user_id: string,
  weekly_slots: [{ dow:0-6, start:'HH:MM', end:'HH:MM',
                   env:'home'|'study'|'academy'|'school'|'transit'|'etc' }],
  exceptions: [{ date:ISODate, delta:'off'|'add', slots?:[...] }]
}

// 3) plan — 계획 (콘텐츠 기획서 §2 원형 + 확장)
plan {
  id, user_id, goal_ref,                    // journey.goal 참조
  period: { start:ISODate, end:ISODate },
  items: [{
    content_ref: string,                    // 콘텐츠 DB 키(인강 시드 id 또는 교재 slug)
    total_units: number,                    // 총 분량(강 수·페이지·문제 수)
    unit_type: 'lecture'|'page'|'problem',
    split_mode: 'per_day'|'d_day',          // 하루 n개 vs D-day 역산
    per_day?: number, target_date?: ISODate,
    study_pattern: 'daily'|'alt'|'no_weekend'|'custom',
    custom_days?: [0-6][],                  // pattern=custom일 때
    env_pref?: env[]                        // 이 콘텐츠에 적합한 환경(배정 힌트)
  }]
}

// 4) todo — 일 단위 원장 = 유일한 사실원 (기획서 §4)
todo {
  plan_id, date: ISODate,
  tasks: [{ content_ref, unit_label:string, qty:number,
            done:boolean, done_ts?:ISO, carried_from?:ISODate }],
  locked:boolean                            // paced_lock(재진단 게이트)
}
// 주·월·시즌 뷰는 todo 집계 함수로만 산출 — 별도 저장 금지(이중 장부 금지)

// 5) ghost_track — 고스트 파트너 (기획서 §13, D-005)
ghost_track {
  id, label: 'constructed',                 // v1은 'constructed' 고정(라벨 필수)
  persona: { nickname, start_band:string, goal_label:string },  // 실존 인물 표현 금지
  weekly_pace: [{ week:number, hours_by_subject:{[subject]:number},
                  milestone?:string }],
  slump_weeks: number[]                     // 현실 페이스: 슬럼프 구간 포함
}

// 6) cohort — 플래너 반 (기획서 §14, D-006)
cohort {
  id, band:string, season:string, capacity:number,   // 기본 25
  members: [{ anon_id, nickname, joined:ISODate, dormant:boolean }],
  // 빌보드는 저장하지 않고 주간 집계 함수로 산출(아래 §2-4)
}
```

## 2. 엔진 4종 — 입출력 계약·산식

### 2-1. 분배 엔진 `distribute(planItem, availability, period) → todo[]`
- study_days = period 내에서 study_pattern 적용한 날짜 목록(exceptions 반영).
- `per_day` 모드: 매 study_day에 per_day 개 배정, total 소진 시 종료(예상 종료일 반환).
- `d_day` 모드: units_per_day = ceil(total_units / study_days.length), 마지막 날 잔여 조정.
- env 배정 규칙(기본 매핑, 정책값화 전제): transit→lecture(인강·암기), study→problem, home→오답·정리. env_pref가 있으면 우선.
- 엣지: study_days=0 → 오류 반환(빈 계획 금지) / total_units < study_days → 격일 자동 압축 제안 플래그.

### 2-2. 이월 엔진 `carryOver(todos, mode) → todo[]` (기획서 §5-1, 옵션 2택)
- `mode:'keep_deadline'`(기간 사수): 미완 qty를 잔여 study_days에 가중 재분배.
  단 일일 상한 초과 시(daily_cap = 기존 최대 배정량 × 1.5) 재분배 불가 플래그 + 'extend' 제안.
- `mode:'keep_pace'`(강도 사수): 완료일 = today + ceil(remaining_units / avg_daily_done).
  avg_daily_done = 최근 28일 실제 완료량 평균(표본 7일 미만이면 계획량으로 대체).
- 이월 task에는 `carried_from` 기록(연쇄 이월 추적).

### 2-3. 실행능력 계수 `execRate(todos, window=28d) → {rate, needed_weeks, options}`
- rate = Σ완료 qty / Σ계획 qty (기간 내, 표본 7일 미만 → null 반환).
- needed_weeks = ceil( remaining_units / (planned_units_per_week × rate) ).
- 반환 예: 계획 12주·rate 0.62 → needed_weeks 19 → options = ['extend','add_hours','reduce_scope'].
- 테스트 필수 케이스: rate=0(전량 미완) → needed_weeks=Infinity 처리(별도 상태 'stalled').

### 2-4. 반·빌보드 집계 `weeklyBoard(cohort, todos_by_member, week) → board`
- 집계 창: 월 00:00 ~ 일 24:00. 반환 4부문(각 top3 + 본인 순위 구간):
  - completed: Σ완료 qty
  - streak: 연속 study_day 완수일 수
  - recovery: (전일 미완 → 당일 전량 완수) 발생 횟수
  - self_best: 본인 직전 4주 최고 주간 완료량 대비 증가율
- 규칙: 성적 입력 없음(타입 차원에서 불가), 하위 순위 미반환(상위 구간 %만), dormant 멤버 제외.
- 편성 `assignCohort(user{band,season}, cohorts) → cohort`: 동일 band+season 중 정원 미달 반에 배정, 없으면 신설.

## 3. 테스트 케이스 (S1 완료 기준 — 전부 통과해야 체크)

1. d_day 분배: 총 60문제·주말 제외·4주(20 study_days) → 일 3문제, 마지막 날 잔여 정확.
2. per_day 분배: 하루 1강·격일·총 10강 → 예상 종료일 = 19일 후.
3. env 배정: transit 슬롯만 있는 날에 problem 배정 금지(lecture 우선).
4. 이월 keep_deadline: 3일 미완 9문제 → 잔여 7일에 가중 분배, cap 초과 시 extend 플래그.
5. 이월 keep_pace: avg_daily_done 2·잔여 20 → 완료일 +10일.
6. execRate: 계획 100·완료 62 → 0.62, 12주 계획 → needed 19주(위 산식 검산).
7. execRate 표본 부족(5일) → null. 완료 0 → 'stalled'.
8. 빌보드: 멤버 5명 목데이터 → 4부문 top3 정확, dormant 제외, 성적 필드 주입 시 타입 오류.
9. 편성: 정원 25 초과 시 신규 반 생성.
10. journey 미성년(elem·middle·high)에 consent.guardian=false → 생성 거부.

## 5. 구현 정정 (S1 착수 시 확정 — 2026-07-24)

본 스펙으로 `packages/janus-planner` 를 구현하며 문서 내부의 모순 2건을 아래와 같이 확정했다.

**(a) `needed_weeks` = 올림(ceil) — 예시·테스트의 "19주"는 20주로 정정.**
§2-3 산식은 `ceil` 인데 같은 절의 예시와 §3-6 테스트는 19주로 적혀 있다. `12 ÷ 0.62 = 19.35…` 이므로 산식대로면 **20주**다. "목표에 필요한 최소 주수"는 올려 잡아야 미달 계획을 제시하지 않으므로 **산식(ceil)을 정본으로 두고 테스트 기대값을 20으로 수정**했다.
⚠ 후속(사람 태스크): 플래너 기획서 v1.2 §5-2의 제품 카피("12주가 아니라 19주가 필요합니다")가 구현과 어긋난다. 카피 수정 여부를 Decision-Register에 등재해 확정할 것.

**(b) 구현 언어 = TypeScript (§4의 `.js` 제안 대체).**
§3-8 "성적 필드 주입 시 타입 오류"·§2-4 "타입 차원에서 불가"·§5 "타입과 함수만"은 순수 JS로 구현할 수 없다. §0의 금지 사항을 스키마 레벨에서 강제하려면 타입이 필요하므로 `.ts` 로 작성했다(`Sealed<T>` 가 금지 키를 `?: never` 로 봉인). **의존성 0 원칙은 그대로** — 런타임 의존성 없음, devDependencies 는 tsc·vitest 뿐.

**(c) 채택한 해석 — §3-2 "예상 종료일 = 19일 후".**
격일을 기간 시작일부터 이틀 간격으로 두면 10회차는 `start + 18일` 이고 이는 기간의 **19일차**다. 이 읽기가 유일하게 자기정합적이므로 그렇게 구현했다.

**(d) 단위 종류는 3종.**
실행가이드의 S1 프롬프트는 "단위 4종"이라 적었으나 §1-3 `unit_type` 은 `lecture|page|problem` 3종이다. 필드 레벨 사양인 §1을 따랐다(학습일 패턴은 문서대로 4종).
